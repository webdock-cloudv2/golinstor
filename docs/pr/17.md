# client: do not lose the controller's error when the error body is not a list

Refs: LINBIT/linstor-server#560

## Problem

For an HTTP error response, `client.do` decodes the body as `ApiCallError`
(a list of `ApiCallRc`). When the body is a JSON object, the decode fails
and the caller gets only the decode error. The controller's actual message is
lost. Seen with Incus creating instances from an image:

```
Error: Failed instance creation: Failed creating instance from image: Unable to start cloning resource definition: json: cannot unmarshal object into Go value of type client.ApiCallError
```

The controller's real error was "(node B) Failed to access DRBD super-block
of volume <clone>/0". It was in the response, but in a field golinstor
didn't read.

## Cause

`client/client.go:676-680` (master a622d0d) decodes every non-2xx, non-404
body straight into `ApiCallError`. The LINSTOR controller does not always send
a list (details and file:line in LINBIT/linstor-server#560):

- `POST /v1/resource-definitions/{rsc}/clone` answers a failed clone with HTTP
  500 and a `ResourceDefinitionCloneStarted` object, with the `ApiCallRc`
  list in `messages`. This has been the case since linstor-server 9d96b8001
  (2025-09); before that the same object came with 201.
- `GET /v1/files/{f}/status/{node}`, 503: `{"message": "..."}`.
- `POST /v1/nodes/exec/drbd-reactorctl/*`, 400: `{"error": "..."}`.

A proxy or load balancer in front of the controller can also answer with
HTML or an empty body.

## Fix

`client.do` reads the error body (at most 1 MiB) and calls the new
`decodeErrorBody` (`client/apicallerror.go`):

1. a non-empty list of `ApiCallRc` → `ApiCallError`, exactly as before;
2. an object with `messages` → those `ApiCallRc` as `ApiCallError`;
3. a single `ApiCallRc` object (with `ret_code`, the form the OpenAPI spec
   documents for `OperationFailed`) → a one-entry `ApiCallError` keeping its
   return code;
4. an object with `message` or `error` → a one-entry `ApiCallError` with that
   text and the `MaskError` bits set, so error checks keep working;
5. anything else → the new exported `*UnexpectedErrorBody{StatusCode, Body}`
   with the raw body, truncated to 4 KiB (valid UTF-8).

A list larger than the 1 MiB read limit would be cut and end up as
`*UnexpectedErrorBody`; real error lists are a few KiB.

Unchanged: 404 still returns `NotFoundError`, and 2xx handling is untouched.
Callers that use `errors.As(err, &client.ApiCallError{})`,
`IsApiCallError` or `errors.Is(err, client.ApiCallRcErr(...))` see the same
values as before for list bodies.

Changed, where the old behaviour was a decode error anyway: an empty list
`[]` or a body that is not JSON now gives `*UnexpectedErrorBody` instead of
an empty `ApiCallError` or a `*json.SyntaxError` / `*json.UnmarshalTypeError`.

## Tests

`client/errorbody_test.go`:
- `TestDecodeErrorBody`, table-driven: list, clone object with `messages`
  (error report id kept), single `ApiCallRc` object (return code kept),
  `messages` winning over a top-level `message`, `{"message"}`, `{"error"}`,
  `null`, a list of non-objects, `[]`, HTML, empty body, a body over 1 MiB
  kept truncated to 4 KiB; error bits checked on every returned `ApiCallRc`;
- `TestCloneErrorKeepsControllerMessage`: `httptest` server answering a clone
  with 500 and the clone-started object; `ResourceDefinitions.Clone` returns
  an `ApiCallError` containing the controller's message. This test fails
  without the fix.

`go vet ./client/` and `go test ./...` pass (Go 1.26.8, linux/amd64).
